# 流程引擎路由策略 (Flow Routing Architecture) 设计方案

## 1. 核心业务痛点描述

在目前的流程引擎架构下，题目的内容（Question Data）和题目的播放流程（Flow Module）已经解耦。通过“路由绑定策略（Flow Profile）”，我们可以决定哪种情况使用哪个流程。

**初步设想：**
*   **前端极致解耦：** 教研老师在编辑器录入题目时，完全不用关心流程绑定，也不用在每个题目下去选地区。
*   **隐式路由下发：** 系统根据当前登录用户的注册地区（如：成都），自动为其分发与之绑定的“成都版听后选择”流程。

**引发的深层业务挑战：**
1.  **跨区体验诉求（痛点 A）：** 成都的用户如果购买了《北京中考全真模拟卷》，他们期望体验的是“北京版的做题流程”，而不是被系统写死只能用“成都流程”。
2.  **子区域细分特化（痛点 B）：** 成都市高新区为了某次联考，希望采用类似“上海版”的特殊流程，而不想随大流使用“成都通用流程”。如何在这种层级关系中实现特例重载？

---

## 2. 架构演进：从“用户身份绑定”到“上下文动态解析”

为了解决上述灵活性危机，路由引擎决不能把规则焊死在单一维度（如 `User.Region`）上。我们必须引入 **上下文透传（Context Override）** 与 **优先级链（Priority Resolution Chain）** 机制。

### 2.1 请求计算的上下文参数 (Context)
当客户端请求一道题目的完整渲染数据时，必须提供尽可能多的上下文，而不是只有用户身份：

```json
{
  "user": {
    "region": "chengdu",
    "district": "gaoxin"
  },
  "task": {
    "examType": "mock_exam",
    "paperRegionMode": "beijing" // 关键：试卷本身带有模式倾向
  }
}
```

### 2.2 多级路由优先级覆盖机制 (Resolution Chain)
服务端的路由计算引擎（Rule Engine）在查表时，必须遵循严密的自上而下的降级匹配逻辑（优先级从高到低）。一旦命中，立即返回对应的 Flow ID。

| 优先级 | 判定层级 (Level) | 匹配规则说明 | 解决的业务痛点 |
| :--- | :--- | :--- | :--- |
| **最高** | **题目硬绑定 (Question Override)** | 该题目 JSON 数据中是否被教研显式干预，写死了专属 `flowId`？ | 极特殊题目的强定制场景 |
| **高** | **试卷/任务级别 (Task/Exam Level)** | 当前用户正在做的这份试卷或作业，是否被指定了某套模式？（如：`paperRegionMode === 'beijing'`） | **解决痛点 A：** 成都人做北京卷，体验北京流程 |
| **中** | **子区域/特定人群 (Sub-Region Level)** | 判断 `district === 'gaoxin'` 是否有特殊配置的路由规则？ | **解决痛点 B：** 高新区脱离成都大盘，使用独立流程 |
| **低** | **大区/省市级 (Region/Province Level)** | 判断 `user.region === 'chengdu'` 是否有配置路由规则？ | 大盘用户的常规隐式路由分配 |
| **兜底** | **全局标准版 (Global Default)** | 以上所有条件全落空时，强制使用的系统预设流程。 | 保底策略，确保应用不崩溃，降低教研配置压力 |

## 3. 系统各端职责划分

基于上述设计，前后端在路由生态中的职责应该被明确界定：

### 3.1 前端 (TestPaperEditor 教研端)
*   **出题页面（日常核心态）：** 保持极简，**完全隐藏路由复杂度**。老师只管录入文本和音频，不需要点选任何规则。
*   **策略管理后台（高级配置态）：** 提供一个名为“流程绑定策略配置 (Flow Profile Management)”的独立页面。运营人员可以在此页面像配置防火墙规则一样，新增“如果 [条件组合] 则使用 [流程版本X]”的全局规则表。

### 3.2 引擎层 (Frontend App Engine / Backend Resolver)
*   **职责：计算与撮合。**
*   接收客户端传来的 Context 和全局规则表，利用刚刚定义的【多级路由优先级】算法，快速算出一个命中的 `FlowModule`，并将其与 `QuestionTemplate` 合并，最终交给 `QuestionRenderer` 进行无脑渲染。

### 3.3 服务端 (Backend Storage)
*   作为策略数据的大型仓库。
*   提供 API 用于持久化保存运营人员配置好的规则表（Priority Policy Rules）。
*   *(进阶)* 服务端可在下发试卷 API 时，直接在服务端利用内存缓存跑完这套路由解析算法，把最终确定的组装数据推给客户端，进一步减轻前端 App 的计算压力。

---

## 4. 方案优势总结

1.  **极大降低教研负担：** 90% 以上的题目落入兜底通用流程或大区隐式流程，出题老师完全无感。
2.  **无限的业务扩展性：** 应对“跨区教辅销售”、“新题型A/B测试”、“按年级分发不同语速流程”等花式需求时，开发人员一行代码都不用改，只需在后台新增一条高优先级的配置规则即可瞬间生效。
3.  **高度解耦：** 题目数据（做什么）与流程图纸（怎么播）解绑，路由策略（什么人在什么场景下怎么播）作为独立中间件，三者互不干扰，架构非常干净。
