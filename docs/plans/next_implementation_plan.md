# 下一阶段实现计划（v1 地区路由）

更新时间：2026-02-26

## 目标

把“题库 + 流程线 + 地区路由”跑成线上可用闭环：

- 编辑器可配置流程线和地区绑定。
- 服务端可稳定决策“该用户命中哪条流程线”。
- 客户端按服务端结果执行流程。

## P0（必须先做）

1. 服务端路由解析接口落地
- 实现 `/api/flow/resolve`
- 输入：`questionId`, `questionType`
- 服务端基于用户身份获取 `region`，返回 `moduleRef`
- 验收：相同用户上下文下命中稳定且可复现。

2. 服务端规则存储与唯一性约束
- 实现 `questionType + region` 唯一约束
- 强制保留 `default` 规则
- 禁止规则引用已归档流程线
- 验收：无冲突写入；错误配置被拒绝并给出原因。

3. 编辑器规则写入改为走服务端
- 前端“地区匹配”从本地存储切为 API 持久化
- 保留本地草稿态，但发布前必须服务端校验
- 验收：刷新后配置一致，且多端读到同一规则。

## P1（上线前建议完成）

1. 端到端链路切换
- 预览/做题运行时默认走服务端 resolve
- 客户端只执行，不再本地二次决策
- 验收：线上与编辑器模拟结果一致。

2. 可观测与排障
- 记录 resolve trace：`userId/questionType/region/ruleId/moduleRef`
- 增加按 ruleId 的命中统计
- 验收：可按问题快速定位“命中哪条规则、为什么命中”。

3. 回滚能力
- 支持一键将某地区回退到标准流程
- 支持规则变更审计（谁改的、何时改的、改了什么）
- 验收：异常时 5 分钟内可完成回退。

## P2（稳定后再做）

1. 灰度能力
- 地区内按比例灰度到新流程线

2. 细粒度维度
- 扩展到 `district/scene/grade`（仅在业务明确需要时）

3. 跨区策略
- 支持“成都用户体验北京流程”等运营场景

## 数据规模收益复述（报告可直接引用）

以 5 个地区举例：

- 不做路由：1W 题约变 5W，5W 题约变 25W（题库复制）
- 做地区路由：题库仍是 1W / 5W，仅新增流程线和映射规则

直接收益：

1. 题库不膨胀，内容维护成本线性可控。
2. 地区差异改“流程”即可，不需要复制题目。
3. 故障回滚只改规则，不改题库。

## 风险与控制

1. 风险：服务端路由成为关键路径
- 控制：缓存 + 超时降级到标准流程

2. 风险：规则误配影响整批用户
- 控制：唯一性校验 + 发布前检查 + 审计日志

3. 风险：运营理解成本
- 控制：只保留“地区绑定”单一模型，先不开放复杂维度

## 里程碑建议

1. M1（1 周）：P0 全部完成（接口、约束、写入）
2. M2（1 周）：P1-1/P1-2（运行链路、可观测）
3. M3（0.5~1 周）：P1-3（回滚与审计）

上线门槛：P0 + P1-1 完成并通过联调验收。
